# 도메인 요구 조건 초안 작성

## 1. 목적과 경계

도메인 계층의 요구 조건을 5원칙에 맞춘 문서로 **로컬 파일에** 쓴다. 사용자는 그 파일에서 직접 검토하고 빈칸을 채운다. 스킬은 파일을 다시 읽어 재검토하고, 사용자가 승인하면 문서를 확정 상태로 고정한다.

- 이 스킬이 하는 일: 입력에서 규칙을 뽑아 초안 파일을 쓰고, 빠진 값과 모호한 곳을 파일 안 질문으로 만든다. 사용자 기입을 반영해 재검토하고, 승인 시 상태를 고정한다.
- 이 스킬이 하지 않는 일:
  - 확정 판단. 확정은 사용자의 명시적 승인으로만 한다.
  - 초안 본문을 대화 메시지로만 전달하기. 문서는 항상 파일로 남긴다.
  - 입력에 없는 값·규칙을 지어내 채우기. 작성자 판단은 할 수 있으나 `[판단]`·`[제안]`으로 표시하고 근거 없는 확정값처럼 쓰지 않는다.
  - 세세한 결정까지 모두 묻기. 질문은 확신이 낮은 결정에만 쓴다(2.2의 3).
  - 저장 구조, API, 화면, 코드 설계.

## 2. 절차

문서는 상태 3단계를 거친다: `초안` → `검토 중` → `확정`. 상태는 문서 맨 위 `상태:` 줄에 적는다.

### 2.1 저장 위치 정하기

1. 사용자가 경로를 지정했으면 그곳에 쓴다.
2. 지정이 없으면 프로젝트 진입 문서(`AGENTS.md`, `CLAUDE.md` 등)에 정해진 요구 조건 문서 위치를 따른다.
3. 둘 다 없으면 쓰기 전에 사용자에게 경로를 묻는다. 임의로 정하지 않는다.
4. 같은 대상의 파일이 이미 있으면 새로 만들지 않고 2.3 재검토로 간다.

### 2.2 초안 작성 (상태: 초안)

1. **입력 수집**: 사용자 요청, 기존 문서, 기존 코드 중 사용자가 지정한 것을 읽는다. 입력이 없으면 대상 도메인과 범위를 먼저 묻는다.
2. **초안 작성**: 3절 원칙에 따라 4절 양식으로 파일에 쓴다. 문장마다 출처를 붙인다.
   - `[입력]`: 입력에 근거가 있다(가능하면 `파일:위치` 또는 인용).
   - `[판단]`: 입력에 근거가 없지만 작성자 확신이 20%를 넘어 작성자가 정한 값이다. "판단 메모"에 근거와 함께 남기며, 사용자는 메모를 보고 뒤집을 수 있다.
   - `[제안]`: 입력에 근거가 없고 작성자 확신이 20% 이하인 값이다. 사용자 확인 전까지 유효하지 않다.
   - `[기입 필요]`: 제안할 근거조차 없어 값을 비워 두고 사용자에게 묻는다.
3. **확신 분류**: 입력에 근거가 없는 결정마다 "사용자가 이 답을 그대로 받아들일 확률"을 작성자가 추정한다.
   - **20% 초과 → `[판단]`**: 작성자가 정하고 "판단 메모"에 남긴다. 묻지 않는다.
   - **20% 이하 → `[제안]` 또는 `[기입 필요]`**: "검토 요청" 질문으로 만든다.
   - 확신을 낮게 보는 신호: 그럴듯한 답이 둘 이상이고 갈림이 비즈니스 결과(금액·권한·되돌릴 수 없는 소멸·외부 약속)를 바꾼다, 입력끼리 모순된다, 같은 성격의 기존 규칙·관례가 없다.
   - 확신을 높게 보는 신호: 같은 저장소·도메인에 같은 성격의 선례가 있다, 업계 관례가 하나로 수렴한다, 틀려도 나중에 바꾸는 비용이 작다.
   - **고영향 결정은 확신과 무관하게 묻는다**: 갈림이 노출 여부(누구에게 보이는가), 권한, 금액, 되돌릴 수 없는 소멸을 바꾸는 결정은 입력에 직접 근거가 있을 때만 `[입력]`으로 쓰고, 그렇지 않으면 확신 %와 상관없이 `[제안]` 질문으로 올린다. 사용자가 보는 결과를 바꾸는 결정은 "틀려도 바꾸는 비용이 작다"로 보지 않는다.
   - 판단 메모는 결정 하나마다 쓰지 않고 **전체를 본 뒤** 묶어서 쓴다: 어떤 방향(예: "보수적으로 차단 쪽", "기존 모듈과 같은 관례")으로 판단했는지, 그 근거, 개별 결정 목록을 남긴다.
4. **질문 정리**: `[제안]`과 `[기입 필요]`를 모두 4절의 "검토 요청" 문답 블록으로 만든다. 사용자의 결정 부담을 줄이기 위해 질문마다 다음을 지킨다.
   - 왜 묻는지(배경)를 한두 줄로 쓴다.
   - 작성자의 **제안 답**과 그 근거를 먼저 적는다. 사용자는 "제안대로"만 써도 된다.
   - 선택지를 고르게 하지 않는다. 사용자는 `사용자:` 줄 아래에 자연어로 자유롭게 쓴다.
5. **자가 점검**: 5절 점검표로 초안을 확인한다. 점검은 형식을 보는 것이지 내용 확정이 아니다.
6. **안내**: 대화에는 본문을 붙이지 않고 파일 경로, 검토 요청 개수, 판단 메모 개수, "질문의 `사용자:` 칸에 기입하고, 뒤집을 판단 메모가 있으면 메모 아래에 적은 뒤 재검토를 요청하라"는 안내만 한다.

### 2.3 재검토 (상태: 검토 중)

사용자가 파일에 기입한 뒤 재검토를 요청하면:

1. 파일을 다시 읽는다. 사용자가 본문을 직접 고친 부분도 사용자 입력으로 존중한다.
2. `사용자:` 답이 명확하면 본문 해당 항목에 반영하고 표시를 `[입력]`(사용자 답변)으로 바꾼다. 해결된 문답 블록은 통째로 "반영 이력"으로 옮긴다.
3. 답이 원칙(3절)과 어긋나거나(예: 숫자 대신 "적당히"), 다른 항목과 모순되거나, 모호하면 같은 블록 아래에 `작성자:` 답글로 이유와 새 제안 답을 적고, 빈 `사용자:` 줄을 다시 연다. 같은 질문은 한 블록 안에서 이어지는 대화로 남긴다.
4. 판단 메모 아래에 사용자가 이견을 적었으면 본문을 고치고 표시를 `[입력]`(사용자 답변)으로 바꾼다. 이견이 모호하면 그 판단을 "검토 요청" 질문으로 옮긴다. 이견이 없는 판단 메모는 그대로 둔다.
5. `사용자:`가 비어 있는 질문은 건드리지 않는다. 비어 있다고 제안 답을 채택하지 않는다.
6. 사용자 답으로 새로 드러난 결정도 2.2의 3 확신 분류를 거친다.
7. 상태를 `검토 중`으로 바꾸고, 남은 질문 개수를 알린다.
8. 남은 질문이 0개가 될 때까지 2.3을 반복한다.

### 2.4 확정 (상태: 확정)

1. 남은 질문이 0개이고 `[제안]`·`[기입 필요]` 표시가 없을 때만 확정을 제안한다. 제안할 때 남아 있는 `[판단]` 개수를 함께 알리고, 확정 승인은 판단 메모 승인을 포함한다고 밝힌다.
2. 사용자가 명시적으로 승인하면 문서를 **완성본**으로 다시 쓴다. 승인 없이 확정하지 않는다.
   - 남기는 것: 범위, 용어, 식별자, 불변식(REQ), 주체와 정책, 경계값과 기본값, 상태와 전이. 4절 "완성본 양식"을 따른다.
   - 지우는 것: `표시:` 줄, 기입 방법 안내, 판단 메모, 검토 요청, 반영 이력, 문장·칸의 `[입력]`·`[판단]` 표시와 `출처` 열, RQ·JD 번호 참조.
   - REQ 번호는 바꾸지 않는다. 다른 문서가 REQ 번호로 가리키기 때문이다.
   - 상태를 `확정`으로 바꾸고 확정일을 적는다. 완성본에는 "결정 과정: 확정 직전 버전의 git 이력" 한 줄만 둔다.
   - 확정 승인은 git 기록 승인을 포함한다. 문답 과정이 사라지지 않도록 **확정 직전 문서를 먼저 커밋**하고, 그다음 완성본을 따로 커밋한다. 기본 브랜치라면 작업 브랜치를 먼저 만든다.
   - 완성본으로 다시 쓴 뒤 규칙의 의미가 바뀌지 않았는지 확정 직전 본문과 대조하고, 바뀐 곳이 있으면 확정하지 않고 보고한다.
3. 확정된 문서를 바꾸려면 사용자 요청이 있어야 하며, 바꾸는 순간 상태를 `검토 중`으로 되돌리고 `표시:` 줄과 "검토 요청"·"반영 이력" 절을 다시 연다. 변경 항목은 새 반영 이력에 남긴다. 기존 규칙은 `[입력]`(확정본)으로 본다.

## 3. 작성 원칙

### 원칙 1. 기술 메커니즘을 빼고 불변식을 쓴다

- **무엇이 항상 참인가**를 쓴다. 어떻게 저장·전달하는가(테이블, 컬럼, 프로토콜, 상태 코드, 화면 배치, 프레임워크 문법)는 쓰지 않는다.
- 엔티티가 생명주기 내내 깨뜨릴 수 없는 일관성 규칙을 명시한다.
  - 예: "총액은 항목 금액의 합과 같다", "잔여 수량은 0 미만이 될 수 없다".
- 입력이 기술 용어로 되어 있으면 그 뒤의 도메인 의미로 바꿔 쓰고, 의미가 불분명하면 질문으로 남긴다.

### 원칙 2. 유비쿼터스 언어와 식별 체계를 정한다

- 핵심 용어(명사·동사)를 정의하고 한 개념에 이름 하나만 쓴다. 입력에서 같은 개념에 여러 이름이 쓰였으면 하나를 제안하고 질문으로 남긴다.
- 고유 식별자는 형식(문자 집합·길이), 생성 방식(자연 키·생성 키·복합 키), 유일성 범위를 쓴다. 빠진 항목은 `[기입 필요]`로 둔다.

### 원칙 3. 주체와 정책을 분리한다

- 주체(누가)와 정책(무엇을 할 수 있는가)을 따로 정의한 뒤 조합한다.
- "누가"와 함께 "어떤 조건·상태에서"를 쓴다. 소유권, 위임·상위 권한자 예외, 익명/인증 상태별 차등을 명시한다.
  - 예: "생성한 주체만 수정할 수 있고 상위 권한자는 소유와 무관하게 수정할 수 있다. 종료 상태에서는 상위 권한자도 수정할 수 없다".

### 원칙 4. 경계값과 기본값을 숫자로 정한다

- '적절한', '충분한', '비어 있지 않은' 같은 표현을 쓰지 않는다. 입력에 이런 표현이 있으면 숫자를 묻는 질문으로 바꾼다.
- 측정 가능한 값(길이·개수·금액·기간)마다 최소·최대·포함 여부를 숫자로 쓴다. 상한이 없으면 "상한 없음"으로 명시한다.
- 값이 주어지지 않았을 때 쓰는 기본값의 유무와 값을 쓴다.

### 원칙 5. 생명주기를 상태와 전이로 쓴다

- 가능한 상태, 상태 사이의 전이와 그 트리거를 나열한다.
- 상태별로 허용되는 행위와 차단되는 행위를 쓴다.
  - 예: "취소 상태에서는 진행 시작이 일어날 수 없다".
- 소멸 방식(논리 삭제·보관·물리 삭제), 소멸 뒤 읽기·쓰기 가능 여부, 연관 엔티티에 미치는 규칙을 쓴다. 입력에 없으면 질문으로 남긴다.

## 4. 초안 양식

규칙마다 번호(`REQ-1`, `REQ-2` …)를 붙여 검토 답변에서 가리킬 수 있게 한다. 번호 접두어가 대상 프로젝트의 기존 번호 체계와 겹치면 바꾸고 그 사실을 알린다.

```markdown
# <대상> 도메인 요구 조건

상태: 초안 | 검토 중 | 확정 (확정일: YYYY-MM-DD)
입력: <읽은 자료 목록>
표시: [입력] 근거 있음 / [판단] 작성자 판단, 판단 메모 참조 / [제안] 작성자 제안, 확인 필요 / [기입 필요] 사용자 기입

## 용어
| 용어 | 정의 | 출처 |

## 식별자
| 대상 | 형식 | 생성 방식 | 유일성 범위 | 출처 |

## 불변식
- REQ-1. ... [입력]

## 주체와 정책
| 정책 | 허용 행위 | 주체별 허용 여부 | 추가 조건(소유·상태) | 출처 |

## 경계값과 기본값
| 값 | 최소 | 최대 | 기본값 | 출처 |

## 상태와 전이
| 현재 상태 | 행위(트리거) | 다음 상태 | 차단 조건 | 출처 |
- 소멸: 방식 / 소멸 후 읽기·쓰기 / 연관 엔티티 처리

## 판단 메모
```

## 5. 자가 점검표

초안 작성과 재검토 회차가 끝날 때마다 확인한다.

- [ ] 문서가 파일로 저장되었고, `상태:` 줄이 현재 단계와 맞다.
- [ ] 사용자 승인 없이 `확정`으로 바꾸지 않았다.
- [ ] (확정 시) 완성본에 표시·출처·판단 메모·검토 요청·반영 이력·RQ/JD 참조가 남아 있지 않고, REQ 번호와 규칙 의미가 확정 직전 본문과 같다.
- [ ] (확정 전) 모든 문장·칸에 `[입력]`·`[판단]`·`[제안]`·`[기입 필요]` 중 하나가 있다.
- [ ] 검토 요청 질문은 모두 확신 20% 이하 결정이다. 확신이 더 높은 결정을 질문으로 올리지 않았다. 단, 고영향 결정(노출 여부·권한·금액·되돌릴 수 없는 소멸)은 확신과 무관하게 질문으로 올렸다.
- [ ] `[판단]` 중에 입력 근거 없는 고영향 결정이 없다.
- [ ] `[판단]`마다 판단 메모에 근거·확신·틀릴 때 영향이 있고, 전체 판단 방향이 적혀 있다.
- [ ] `[제안]`과 `[기입 필요]`가 모두 "검토 요청"에 문답 블록으로 있다.
- [ ] 문답 블록마다 배경, 근거 있는 제안 답, 빈 `사용자:` 줄이 있고 선택지 체크를 요구하지 않는다.
- [ ] `[입력]` 항목은 입력에서 근거를 가리킬 수 있다.
- [ ] 기술 메커니즘 용어(저장·전송·화면·프레임워크)가 규칙 문장에 없다. (원칙 1)
- [ ] 같은 개념에 다른 이름을 쓰지 않았다. (원칙 2)
- [ ] 식별자마다 형식·생성 방식·유일성 범위가 채워졌거나 질문으로 있다. (원칙 2)
- [ ] 행위마다 주체와 조건이 채워졌거나 질문으로 있다. (원칙 3)
- [ ] 추상적 수량 표현이 없고, 측정 가능한 값마다 경계·기본값이 채워졌거나 질문으로 있다. (원칙 4)
- [ ] 상태마다 허용·차단 행위, 소멸 후 처리가 채워졌거나 질문으로 있다. (원칙 5)
- [ ] 규칙마다 번호가 있다.

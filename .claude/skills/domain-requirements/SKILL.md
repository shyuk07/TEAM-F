# 도메인 요구 조건 초안 작성

## 1. 목적과 경계

도메인 계층의 요구 조건을 5원칙에 맞춘 **초안**으로 만들어 사용자에게 넘긴다. 사용자는 초안을 검토하고 빈칸을 채운다.

- 이 스킬이 하는 일: 입력에서 규칙을 뽑아 초안으로 정리하고, 빠진 값과 모호한 곳을 질문으로 만든다.
- 이 스킬이 하지 않는 일:
  - 요구 조건 확정. 확정은 사용자가 한다.
  - 입력에 없는 값·규칙을 지어내 채우기. 제안은 할 수 있으나 "제안"으로 표시하고 확정값처럼 쓰지 않는다.
  - 저장 구조, API, 화면, 코드 설계.

## 2. 절차

1. **입력 수집**: 사용자 요청, 기존 문서, 기존 코드 중 사용자가 지정한 것을 읽는다. 입력이 없으면 대상 도메인과 범위를 먼저 묻는다.
2. **초안 작성**: 3절 원칙에 따라 4절 양식으로 쓴다. 문장마다 출처를 붙인다.
   - `[입력]`: 입력에 근거가 있다(가능하면 `파일:위치` 또는 인용).
   - `[제안]`: 입력에 근거가 없고 작성자가 제안하는 값이다. 사용자 확인 전까지 유효하지 않다.
   - `[기입 필요]`: 값을 비워 두고 사용자에게 묻는다.
3. **질문 정리**: `[제안]`과 `[기입 필요]`를 모두 4절의 "검토 요청" 목록에 모은다. 질문은 사용자가 한 줄로 답할 수 있게 쓴다(선택지가 있으면 함께 적는다).
4. **자가 점검**: 5절 점검표로 초안을 확인한다. 점검은 초안의 형식을 보는 것이지 내용 확정이 아니다.
5. **전달**: 초안을 사용자가 지정한 위치에 쓰거나, 지정이 없으면 응답 본문으로 전달한다. 저장 위치를 임의로 정하지 않는다. 전달할 때 "초안이며 확정되지 않았다"와 검토 요청 개수를 함께 알린다.

사용자가 답을 주면 해당 항목의 표시를 `[입력]`(사용자 답변 근거)으로 바꾸고, 새로 생긴 모호함이 있으면 다시 질문으로 남긴다.

## 3. 작성 원칙

### 원칙 1. 기술 메커니즘을 빼고 불변식을 쓴다

- **무엇이 항상 참인가**를 쓴다. 어떻게 저장·전달하는가(테이블, 컬럼, 프로토콜, 상태 코드, 화면 배치, 프레임워크 문법)는 쓰지 않는다.
- 엔티티가 생명주기 내내 깨뜨릴 수 없는 일관성 규칙을 명시한다.
  - 예: "총액은 항목 금액의 합과 같다", "잔여 수량은 0 미만이 될 수 없다".
- 입력이 기술 용어로 되어 있으면 그 뒤의 도메인 의미로 바꿔 쓰고, 의미가 불분명하면 질문으로 남긴다.

### 원칙 2. 유비쿼터스 언어와 식별 체계를 정한다

- 핵심 용어(명사·동사)를 정의하고 한 개념에 이름 하나만 쓴다. 입력에서 같은 개념에 여러 이름이 쓰였으면 하나를 제안하고 질문으로 남긴다.
- 고유 식별자는 형식(문자 집합·길이), 생성 방식(자연 키·생성 키·복합 키), 유일성 범위를 쓴다. 빠진 항목은 `[기입 필요]`로 둔다.

### 원칙 3. 주체와 정책을 분리한다

- 주체(누가)와 정책(무엇을 할 수 있는가)을 따로 정의한 뒤 조합한다.
- "누가"와 함께 "어떤 조건·상태에서"를 쓴다. 소유권, 위임·상위 권한자 예외, 익명/인증 상태별 차등을 명시한다.
  - 예: "생성한 주체만 수정할 수 있고 상위 권한자는 소유와 무관하게 수정할 수 있다. 종료 상태에서는 상위 권한자도 수정할 수 없다".

### 원칙 4. 경계값과 기본값을 숫자로 정한다

- '적절한', '충분한', '비어 있지 않은' 같은 표현을 쓰지 않는다. 입력에 이런 표현이 있으면 숫자를 묻는 질문으로 바꾼다.
- 측정 가능한 값(길이·개수·금액·기간)마다 최소·최대·포함 여부를 숫자로 쓴다. 상한이 없으면 "상한 없음"으로 명시한다.
- 값이 주어지지 않았을 때 쓰는 기본값의 유무와 값을 쓴다.

### 원칙 5. 생명주기를 상태와 전이로 쓴다

- 가능한 상태, 상태 사이의 전이와 그 트리거를 나열한다.
- 상태별로 허용되는 행위와 차단되는 행위를 쓴다.
  - 예: "취소 상태에서는 진행 시작이 일어날 수 없다".
- 소멸 방식(논리 삭제·보관·물리 삭제), 소멸 뒤 읽기·쓰기 가능 여부, 연관 엔티티에 미치는 규칙을 쓴다. 입력에 없으면 질문으로 남긴다.

## 4. 초안 양식

규칙마다 번호(`REQ-1`, `REQ-2` …)를 붙여 검토 답변에서 가리킬 수 있게 한다. 번호 접두어가 대상 프로젝트의 기존 번호 체계와 겹치면 바꾸고 그 사실을 알린다.

```markdown
# <대상> 도메인 요구 조건 — 초안 (확정 아님)

입력: <읽은 자료 목록>
표시: [입력] 근거 있음 / [제안] 작성자 제안, 확인 필요 / [기입 필요] 사용자 기입

## 용어
| 용어 | 정의 | 출처 |

## 식별자
| 대상 | 형식 | 생성 방식 | 유일성 범위 | 출처 |

## 불변식
- REQ-1. ... [입력]

## 주체와 정책
| 정책 | 허용 행위 | 주체별 허용 여부 | 추가 조건(소유·상태) | 출처 |

## 경계값과 기본값
| 값 | 최소 | 최대 | 기본값 | 출처 |

## 상태와 전이
| 현재 상태 | 행위(트리거) | 다음 상태 | 차단 조건 | 출처 |
- 소멸: 방식 / 소멸 후 읽기·쓰기 / 연관 엔티티 처리

## 검토 요청
1. (REQ-n / 항목) 질문 — 선택지: A / B / 기타
```

## 5. 자가 점검표

초안을 전달하기 전에 확인한다.

- [ ] 문서 제목과 전달 메시지에 "초안이며 확정 아님"이 있다.
- [ ] 모든 문장·칸에 `[입력]`·`[제안]`·`[기입 필요]` 중 하나가 있다.
- [ ] `[제안]`과 `[기입 필요]`가 모두 "검토 요청"에 질문으로 있다.
- [ ] `[입력]` 항목은 입력에서 근거를 가리킬 수 있다.
- [ ] 기술 메커니즘 용어(저장·전송·화면·프레임워크)가 규칙 문장에 없다. (원칙 1)
- [ ] 같은 개념에 다른 이름을 쓰지 않았다. (원칙 2)
- [ ] 식별자마다 형식·생성 방식·유일성 범위가 채워졌거나 질문으로 있다. (원칙 2)
- [ ] 행위마다 주체와 조건이 채워졌거나 질문으로 있다. (원칙 3)
- [ ] 추상적 수량 표현이 없고, 측정 가능한 값마다 경계·기본값이 채워졌거나 질문으로 있다. (원칙 4)
- [ ] 상태마다 허용·차단 행위, 소멸 후 처리가 채워졌거나 질문으로 있다. (원칙 5)
- [ ] 규칙마다 번호가 있다.

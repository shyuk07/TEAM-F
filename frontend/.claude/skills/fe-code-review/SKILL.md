# 프론트엔드 코드 리뷰

리뷰어는 코드를 고치지 않습니다(감사자 ≠ 수정자). 규칙 ID는 `frontend-invariants`가 정본입니다.

## 1. 입력
발주서에서 아래를 받습니다. 없으면 리뷰를 시작하지 않고 무엇이 없는지 보고합니다.
- 리뷰 대상: diff 범위(예: `git diff HEAD`, `git diff origin/main...HEAD -- frontend/`)
- 변경 의도: 무엇을 바꾸려 했는지, 화면 ID
- 정본: 설계안(`../docs/design/frontend/<slice>.md`), 화면 명세(`../docs/design-system/screens.md`의 화면 ID), API 명세(`../docs/reference/<모듈>.md`)

## 2. 관점

diff 전체를 읽고, 바뀐 함수를 부르는 코드와 바뀐 함수가 부르는 코드까지 따라 읽습니다. 관점마다 확인하고, 해당이 없으면 건너뛰지 않고 "해당 없음"으로 적습니다.

| 관점 | 확인할 것 |
| --- | --- |
| **비동기 경쟁** | 입력이 빠르게 바뀔 때 늦게 온 이전 응답이 새 결과를 덮지 않는가. effect 요청에 `AbortController` 정리가 있는가. 언마운트·abort 뒤 `setState`가 없는가(F10). |
| **중복 제출** | 예약·결제·취소처럼 되돌리기 어려운 요청을 두 번 보낼 수 있는가(더블 클릭, Enter + 클릭). `pending` 동안 버튼이 비활성인가. |
| **상태 분기** | 로딩·빈·에러·권한 없음을 모두 그리는가. 에러 후 다시 시도할 수 있는가. 빈 배열과 로딩을 구분하는가(F10). |
| **렌더·effect** | effect 의존성이 맞는가. 렌더마다 새 객체·함수가 deps에 들어가 무한 요청·무한 렌더가 생기지 않는가. `key`가 배열 인덱스라 항목 상태가 섞이지 않는가. |
| **라우팅·인증** | 로그인이 필요한 화면이 가드되는가. 401·`TOKEN_REVOKED` 처리가 공통 경로로 가는가. 뒤로가기·새로고침에서 상태가 깨지지 않는가(SPA fallback 전제). |
| **명세 일치** | 요청·응답 필드, null 가능 여부, 상태 코드, `error_code` 분기가 명세와 같은가(F14). DTO가 infrastructure 밖으로 새지 않는가(F9). 설계안과 명세가 다르면 임의로 고르지 않고 양쪽 위치를 적습니다. |
| **문구·디자인** | 화면 문구가 `screens.md`와 글자 그대로 같은가(F13). accent·ok 색 사용 원칙을 지키는가(F12). |
| **레이아웃** | 셸 계약(`design-system-usage` §3.2)을 지키는가: `.bar`·`.cta`·`.tabs`가 `.body` 밖에 있는가, 레이아웃·page가 `height`·`overflow`·`position: fixed`로 셸 동작을 따로 만들지 않는가, 오버레이가 `.body` 자리를 대신하는가. 모바일 전용·PC 전용 요소에 `.mob`·`.hide`·`.dk`(§3.1)를 썼는가. 주 버튼이 `.cta`와 `.dk`에 같은 동작으로 있는가. 실제 `<a>`·`<button>`·`<input>`에 preview와 다른 모양이 날 수 있는 곳을 인라인 스타일로 우회하지 않았는가(§3.3). "디자인 시스템에 없다"는 주석·보고는 `bundle.css`를 검색해 사실인지 확인합니다. 렌더 결과는 판정하지 않고 `qa-verification` §4.1 실측 대상으로 적습니다. |
| **시각·숫자** | 마감 시각·남은 분 계산이 시간대(UTC 문자열 → `Date`)를 올바르게 다루는가. 금액 합계·할인율 반올림이 명세와 같은가. |
| **접근성 기본** | 버튼이 `<button>`인가(클릭 가능한 `div` 금지). 입력에 라벨이 있는가. 바텀시트·확인 화면에서 포커스가 갇히고 닫으면 돌아오는가. |
| **보안** | 토큰을 `shared/api/tokenStorage.ts` 밖에서 읽거나 쓰지 않는가. 토큰·개인정보를 로그(`console.log`), URL, React 상태, 에러 보고에 남기지 않는가(F17). `dangerouslySetInnerHTML`·`innerHTML`·`eval`이 없고, 사용자 입력으로 만든 `href`·`src`가 `http(s):`만 허용하는가(F17). 로그아웃·401·비밀번호 변경 뒤 `clearToken()`을 부르는가(`api-client` §2.1). 새 의존성·외부 스크립트가 있으면 승인 여부를 확인했는가. `VITE_` 값에 비밀이 없는가(F15). |
| **주입** | 유스케이스가 포트만 받고 구현체 기본값(`deps.x ?? new HttpX()`)을 두지 않는가. 포트 메서드가 구현체에만 있는 메서드를 부르지 않는가(백엔드 R10과 같음). 새 포트·토큰이 소유 영역의 `features/<영역>/wiring.ts` 한 곳에 등록되고 `app/container.ts`에 연결됐는가. 영역끼리 직접 import하지 않고 entities 포트로 받는가(빠지면 첫 렌더에 "의존성 미등록" 오류). 구조 규칙 자체(F18 자동 검사 항목)는 `fe-architect`가 판정합니다. |
| **작업 주석** | 새 `TODO`·`FIXME`의 태그가 맞는가(시점이 지나면 결함이 될 일을 `TODO`로 남기지 않았는가). `왜:`·`언제:`만 읽고 무엇을 언제 고칠지 알 수 있는가. 이번 범위에서 고칠 수 있는 일을 주석으로 미루지 않았는가. 고친 일의 주석을 지웠는가(F19, `code-annotations` §4). |
| **테스트** | 변경된 동작마다 테스트가 있는가. application·presentation 테스트가 `vi.mock` 대신 가짜 구현체를 넣는가(`layer-architecture` §6.8). 지워지거나 느슨해진 단언(`toBeTruthy`로 바꿈, 기대값 삭제, `skip`)이 있으면 이유가 정당한지(기능 제거, 기대값 변경) 판정합니다(F16). |

추측은 쓰지 않습니다. 코드에서 확인한 사실만 `파일:줄`과 함께 적고, 확신이 낮으면 그렇게 표시합니다.

## 3. 하지 않는 것
- 코드·테스트 수정, 서버·테스트 실행(실행 검증은 `fe-qa`).
- FSD·4계층 구조 판정(F1~F6)은 `layer-check`와 `fe-architect`가 합니다. 정확성에 영향을 주는 경우에만 언급합니다.
- 취향 지적(변수명 선호, 줄바꿈)은 하지 않습니다. 포맷은 Prettier가 정합니다.

## 4. 보고 형식

지적마다 아래 항목을 적습니다.

| 심각도 | 파일:줄 | 관점 | 내용 | 실패 시나리오 | 권장 수정 | 확신도 |
| --- | --- | --- | --- | --- | --- | --- |

- 심각도: **차단**(잘못된 동작·중복 결제·데이터 손상, 머지 불가) / **중요**(명세·문구 불일치, 상태 분기 누락, 회귀를 놓치는 테스트) / **사소**(개선 권장)
- 실패 시나리오에는 구체적인 입력·순서와 그때 화면에 보이는 잘못된 결과를 적습니다.
- 마지막 줄에 판정을 적습니다: 차단 또는 중요 지적이 있으면 **REQUEST_CHANGES**, 없으면 **APPROVE**.
- 지적이 없으면 확인한 관점 목록과 근거(`파일:줄`)를 적습니다.

## 5. 리뷰 루프
- 수정 후 다시 리뷰할 때는 지난 지적이 해결됐는지 먼저 확인하고, 새로 바뀐 부분만 추가로 봅니다.
- 같은 지적이 3회 리뷰 뒤에도 해결되지 않으면 더 반복하지 않고, 양쪽 주장과 근거를 정리해 사용자에게 판단을 요청합니다.

# TDD 작업 순서 (⚠️ 사용자 요청으로 비활성화됨: 빠른 개발 모드 적용 중)

기능 코드는 이 순서로 만듭니다. 오케스트레이션 흐름(`../docs/operations/frontend-orchestration.md` §5)의 "Red 테스트 → 구현 → 점검" 부분을 자세히 정한 정본입니다. 테스트 파일 위치와 작성 방법은 `react-implementation` §7, 검증 명령은 `frontend-invariants` §6을 따릅니다.

## 1. 단계

| 단계 | 담당 | 입력 | 산출물 | 완료 조건 |
| --- | --- | --- | --- | --- |
| 0. 설계 | `fe-architect` | 화면 명세, API 명세 | 설계안과 **테스트 목록**(§2) | 구현을 막는 결정 항목 0건(사용자 확정) |
| 1. 골격 | `fe-developer` | 설계안 공개 API·시그니처 | 타입·포트·토큰·함수·훅·컴포넌트의 빈 구현(§3) | 게이트 중 test 외 전부 통과, 기존 테스트 통과 |
| 2. Red | `fe-qa` | 설계안 테스트 목록, 골격 | `tests/` 아래 테스트 | §4 Red 판정 통과 |
| 3. Red 확인 | 오케스트레이터 | Red 보고 | 재실행 결과 | `npm run test` 출력에서 새 테스트가 **케이스 단위로** 실패하는지 직접 확인 |
| 4. Green | `fe-developer` | Red 테스트, 설계안 | 구현 | 테스트 수정 없이 완료 게이트 전부 통과. `not implemented` 0건 |
| 5. Refactor | 같은 `fe-developer` | Green 결과 | 다듬은 코드 | 테스트·동작 그대로, 완료 게이트 전부 통과 |
| 6. 점검 | `fe-architect`(구조) + `fe-reviewer`(정확성) | diff, 설계안 | 위반·지적 표 | 위반 0, APPROVE |
| 7. 검증 | `fe-qa` | 구현 결과 | `qa-verification` 보고 | PASS |

- 4와 5는 한 발주로 맡길 수 있습니다. 보고에는 Green 시점 결과와 Refactor 뒤 결과를 나눠 적습니다.
- 6에서 코드 결함이 나오면 같은 slice의 `fe-developer`에게 지적 원문을 붙여 재발주하고 5부터 다시 합니다. 테스트 결함(빈틈, 잘못된 기대값)이면 §5 절차로 갑니다.
- 아래 계층부터 진행합니다(`shared` → `entities` → `features` → `widgets` → `pages` → `app`). 독립된 slice는 단계마다 병렬로 맡길 수 있습니다.

## 2. 설계안의 테스트 목록

`fe-architect`는 설계안(`layer-architecture` §5)에 테스트 목록 절을 둡니다. Red를 쓰는 `fe-qa`가 설계안만 보고 테스트를 쓸 수 있어야 합니다.
- 대상별(domain 함수, 유스케이스, 훅, 컴포넌트, 라우트)로 테스트 이름 후보와 기대 결과를 적습니다.
- domain은 경계값(0, 1, 최댓값, 마감 시각 정각, 빈 값), 훅은 상태 전이(로딩 → 성공·빈·에러, 언마운트 abort), 컴포넌트는 화면 상태별 표시(로딩·빈·에러·권한 없음·성공)와 문구 정본 위치를 적습니다.
- 정본이 없어 기대값을 정할 수 없는 항목은 테스트 목록에 넣지 않고 질문 목록에 둡니다.

## 3. 골격

설계안의 공개 API와 시그니처를 그대로 파일로 만들고, 본문은 비워 둡니다. Red가 "모듈 없음"이 아니라 **테스트 하나하나의 실패**가 되게 하는 단계입니다.

```ts
// 함수·유스케이스·훅·구현체 메서드
export function discountRate(offer: Offer): number {
  void offer;
  throw new Error('not implemented: discountRate');
}

// 컴포넌트
export function OfferList(props: OfferListProps) {
  void props;
  return null;
}
```
- 인자는 `void <이름>;`으로 사용 처리합니다. `_` 접두사는 ESLint `no-unused-vars`에 걸리고, 규칙을 끄지 않습니다(F16). Green에서 `void` 줄을 지웁니다.
- 타입, 포트(`interface`), 토큰, 상수, `index.ts` 공개 API, `wiring.ts` 등록은 설계안대로 실제로 만듭니다. 비우는 것은 동작(함수 본문, 컴포넌트 렌더)뿐입니다.
- 설계안에 없는 export를 만들지 않습니다. 시그니처를 정할 수 없으면 멈추고 보고합니다.
- 골격에는 테스트를 쓰지 않습니다.

## 4. Red 판정

| 항목 | 기준 |
| --- | --- |
| 실패 단위 | 새 테스트가 **케이스 단위로 실행되어** 실패한다. 파일 단위 실패(import·문법 오류, "no tests")가 0건 |
| 실패 이유 | `not implemented`, 또는 단언 불일치(컴포넌트가 `null`을 렌더해 요소를 찾지 못함 등). 다른 이유면 테스트를 고친 뒤 다시 확인 |
| Red에서 통과한 테스트 | 0건이 원칙. 골격만으로 통과하는 테스트는 무엇을 확인하는지 다시 보고, 그대로 두려면 이유를 보고 |
| 정적 검사 | `npm run typecheck`, `npm run lint`, `npm run format:check` 통과 |
| 기존 테스트 | 모두 통과 |
| 금지 | `skip`·`only`·`todo`(F16), `vi.mock`으로 application·presentation 대체(`react-implementation` §7) |

보고에는 새 테스트 수, 실패 수, 실패 이유별 개수, Red에서 통과한 테스트 목록을 적습니다.

## 5. 구현 중 테스트를 바꿔야 할 때

Green 단계에서 테스트가 규격(설계안·스킬)이나 다른 규칙(ESLint·타입)과 부딪치면:
1. `fe-developer`는 테스트를 고치지 않고 멈춰서, 테스트(파일:줄)와 부딪치는 규격·규칙(파일:줄)을 나란히 보고합니다.
2. 오케스트레이터가 원인을 나눕니다. 테스트가 규격과 다르면 4로, 규격을 바꿔야 하면 3으로 갑니다.
3. 규격 변경은 사용자가 결정합니다. 정본 수정은 소유자가 합니다(설계안은 `fe-architect`, 스킬은 오케스트레이터).
4. Red를 쓴 `fe-qa`가 테스트를 고치고 바뀐 테스트의 Red를 다시 확인합니다.
5. `fe-developer`가 Green을 이어 갑니다.

- `fe-developer`는 Red 밖의 테스트를 **추가만** 할 수 있습니다. 추가한 테스트는 보고서에 따로 적습니다.
- 테스트를 통과시키려고 공개 타입·시그니처를 설계안과 다르게 바꿔야 하면(예: 타입 인자 기본값 추가), 바꾸기 전에 결정 항목으로 올립니다.

## 6. TDD를 생략하는 작업

아래는 테스트를 먼저 쓰지 않고 완료 게이트만 통과시킵니다.
- 설정 파일, 의존성, 스크립트 변경
- 디자인 시스템 복사본 동기화, 문서, 주석만 바꾸는 변경
- 동작을 바꾸지 않는 이름 변경·파일 이동(기존 테스트가 그대로 통과해야 함)

생략할 때는 발주서와 보고서에 "TDD 생략: <이유>"를 적습니다.

# 작업 주석 (TODO · FIXME · open-issues)

작업 주석은 "지금 고치지 않는 일"을 코드 옆에 남기는 방법입니다. 번호 대신 **주석 하나만 읽어도 무엇을·왜·언제 고칠지 알 수 있게** 쓰고, 작업할 때마다 검색해서 이번에 고칠지 정합니다.

## 1. 태그

| 태그 | 뜻 | 예 |
| --- | --- | --- |
| `FIXME` | 지금은 받아들일 수 있지만 **정해진 시점까지 반드시 고쳐야** 하는 것. 그대로 두면 그 시점에 결함이 된다 | 인증 가드가 항상 통과(auth 구현 전), 임시 응답 처리, 알려진 경계 오류 |
| `TODO` | 하면 좋은 개선, 또는 결정을 기다리는 것. 하지 않아도 지금 동작은 맞다 | 2xx 비JSON 응답을 `ApiError`로 감쌀지, 중복 코드 정리 |
| `open-issues:` | `../docs/design-system/open-issues.md`에 적힌 임시 동작을 그대로 따른 곳. 정본 쪽이 정해지면 고친다 | `// open-issues: O12 사진 1장 제한은 화면에서만` |

- 판단이 애매하면 묻습니다: "그 시점이 지나도 그대로 두면 사용자에게 문제가 생기는가?" 그렇다면 `FIXME`, 아니면 `TODO`.
- `HACK`, `XXX`, `NOTE` 같은 다른 태그는 쓰지 않습니다. 설명이 필요한 코드는 일반 주석으로 씁니다.
- 테스트의 건너뛰기(`it.skip`, `test.fixme`, `it.todo`)는 이 주석으로 대신할 수 없습니다(F16).

## 2. 형식

`TODO`·`FIXME`는 세 줄로 씁니다. 첫 줄은 한 줄 요약, 다음 두 줄은 들여쓴 `왜:`와 `언제:`입니다.

```ts
// FIXME: 인증 가드가 항상 통과한다. 로그인하지 않아도 상점주 화면이 열린다.
//   왜: auth 영역 구현 전이라 세션을 확인할 수단이 없다 (docs/design/frontend/app-shell.md D-9)
//   언제: auth 구현 시, 늦어도 배포 전
```

```ts
// TODO: 2xx인데 본문이 JSON이 아니면 SyntaxError가 그대로 올라간다. ApiError(res.status, 'UNKNOWN')로 감쌀지 정한다.
//   왜: 배포 환경에서 proxy가 빠져 index.html(200)을 받으면 화면이 ApiError로 분기하지 못한다 (fe-reviewer 지적)
//   언제: 결정 후 (사용자: 비JSON 2xx 처리 방식)
```

| 줄 | 쓸 것 |
| --- | --- |
| 요약 | 무엇이 문제이거나 무엇을 할지. 증상이 있으면 증상 |
| `왜:` | 지금 고치지 않는 이유와 근거. 근거는 파일·절, 설계안 D-·C- 번호, 리뷰 지적 출처 |
| `언제:` | 고칠 시점. 아래 §3 표기 중 하나로 시작 |

- 검색할 낱말(영역 이름, 화면 ID, 함수 이름)을 요약이나 `왜:`에 넣습니다. `언제:`도 검색 대상입니다.
- `open-issues:`는 한 줄이면 됩니다. 항목(화면 ID)과 따른 임시 동작을 적습니다.

## 3. "언제" 표기

| 표기 | 뜻 | 누가 확인하나 |
| --- | --- | --- |
| `<영역·slice·화면 ID> 구현 시` | 그 작업을 시작할 때 같이 고친다 (예: `auth 구현 시`, `O11 구현 시`) | 오케스트레이터가 그 작업의 범위를 정할 때 |
| `결정 후 (<누가>: <무엇>)` | 결정이 나면 고친다 | 오케스트레이터가 결정을 받았을 때 |
| `배포 전` | 배포 전까지 반드시 고친다 | 배포 전 점검 |
| `리팩터링 시` | 그 코드를 다시 다듬을 때 (`TODO`만) | 그 파일을 고치는 개발자 |

`FIXME`는 `리팩터링 시`를 쓰지 않습니다. 반드시 고칠 일에는 확인할 사람이 있는 시점을 정합니다. 여러 시점을 함께 쓸 수 있습니다(`auth 구현 시, 늦어도 배포 전`).

## 4. 언제 확인하고 고치나

| 시점 | 누가 | 할 일 |
| --- | --- | --- |
| 범위 확정(발주 전) | 오케스트레이터 | `list --match <영역·화면 ID>`로 검색합니다. `FIXME`는 이번 범위에 넣고 발주서에 원문과 파일:줄을 붙입니다. 이번에 못 고치면 사용자에게 이유를 올립니다. `TODO`는 참고로 붙입니다 |
| 결정을 받았을 때 | 오케스트레이터 | `list --match "결정 후"`에서 그 결정에 걸린 주석을 찾아 소유 개발자에게 수정을 발주합니다 |
| 구현 중 | `fe-developer` | 이번 범위에서 고칠 수 있으면 주석을 남기지 않고 고칩니다. 범위 밖이거나 결정이 필요할 때만 남기고 보고서에 적습니다 |
| 리뷰 | `fe-reviewer` | 새로 생긴 주석의 태그가 맞는지(반드시 고칠 일을 `TODO`로 남기지 않았는지), `왜`·`언제`가 충분한지 확인합니다. 이번에 고치지 않기로 한 지적은 오케스트레이터가 사용자 확인 후 소유 개발자에게 주석 추가를 발주합니다 |
| 머지 전 | `fe-qa` | `check`가 통과해야 합니다. `list` 결과를 보고에 붙입니다. `언제:`가 이번 변경의 작업을 가리키는 `FIXME`가 남아 있으면 머지 불가입니다 |
| 배포 전 | 오케스트레이터 | `list --tag FIXME`가 0건이어야 배포할 수 있습니다. 남아 있으면 항목별로 사용자 결정을 받습니다 |

- 고친 뒤에는 같은 커밋에서 주석을 지웁니다. 시점이 바뀌면 `언제:`를 고치고 이유를 `왜:`에 덧붙입니다.
- 주석을 다는 사람은 그 코드를 쓰는 사람(`fe-developer`, 테스트는 `fe-qa`)입니다. 리뷰어·설계자는 제안만 합니다.

## 5. 스크립트

`src/`, `tests/`, `e2e/`의 `.ts`·`.tsx`·`.css`·`.mjs`를 읽습니다. 디자인 시스템 복사본(`src/app/styles/tokens.css`, `bundle.css`)은 건너뜁니다. 명령은 `frontend` 폴더에서 실행합니다.

```powershell
node .claude/skills/code-annotations/scripts/annotations.mjs list
node .claude/skills/code-annotations/scripts/annotations.mjs list --tag FIXME
node .claude/skills/code-annotations/scripts/annotations.mjs list --match auth
node .claude/skills/code-annotations/scripts/annotations.mjs check
```
- `list`: 태그·파일:줄·요약·왜·언제를 출력합니다. `--tag`(TODO, FIXME, open-issues)와 `--match`(요약·왜·언제에 들어 있는 글자, 대소문자 무시)로 거릅니다. 항상 종료코드 0입니다.
- `check`: 형식 위반이 있으면 종료코드 1입니다. `TODO`·`FIXME`에 `왜:`·`언제:` 줄이 없음, `FIXME`의 `언제:`가 `리팩터링 시`, 금지 태그(`HACK`, `XXX`), 요약이 비어 있음을 잡습니다.
- 주석 형식은 `//`로 시작하는 줄과 `/* */` 안의 줄을 같은 방식으로 읽습니다.

# auth 도메인 요구 조건 — 회원·인증·포인트

상태: 검토 중 (2026-11-06 확정본을 2026-11-10 사용자 결정으로 다시 엶: 미수령 예약 예외. 변경 항목은 맨 아래 "반영 이력")
결정 과정: 확정 직전 버전의 git 이력

## 범위

- 포함: 회원(고객·상점주·관리자)이 겪는 가입 → 로그인·로그아웃 → 내 정보(변경·비밀번호 재설정·탈퇴) → 포인트의 규칙
- 제외: 관리자 모듈이 정하는 상세 규칙(승인·정지·강제 탈퇴의 조건 등). auth가 지켜야 하는 것만 "다른 모듈과의 경계"에 적는다.

## 용어
| 용어 | 정의 |
| --- | --- |
| 회원 | 계정을 가진 모든 사용자. 역할은 고객·상점주·관리자 중 하나다 |
| 고객 | 할인 상품을 예약·결제하는 회원. 회원가입의 기본 대상이다 |
| 상점주 | 상점을 운영하는 회원. 역할 값은 `OWNER`이다 |
| 관리자 | 운영을 맡는 회원. 회원가입으로는 생기지 않는다 |
| 역할 | 회원이 고객·상점주·관리자 중 무엇인지 나타내는 값 |
| 회원가입 | 비회원이 고객 또는 상점주 계정을 만드는 행위 |
| 로그인 | 이메일과 비밀번호가 맞을 때 인증 토큰을 받는 행위 |
| 인증 토큰 | 로그인 성공 시 받는, 정해진 시간 동안 회원임을 증명하는 값 |
| 로그아웃 | 쓰고 있던 인증 토큰을 만료 전에 무효로 만드는 행위 |
| 폐기 토큰 기록 | 무효가 된 인증 토큰의 식별자와 원래 만료 시각의 기록. "블랙리스트"와 같은 개념이다 |
| 내 정보 | 로그인한 회원 본인의 계정 정보와 포인트 잔액 |
| 비밀번호 변경 | 로그인한 회원이 현재 비밀번호를 확인받고 새 비밀번호로 바꾸는 행위 |
| 비밀번호 재설정 | 비밀번호를 잊은 회원이 본인 확인을 거쳐 새 비밀번호를 정하는 행위. "비밀번호 변경"과 다르다 |
| 재설정 코드 | 비밀번호 재설정 때 본인 확인에 쓰는 일회용 값. 회원이 가입한 이메일로 받는다 |
| 탈퇴 | 회원 계정을 더 이상 쓸 수 없게 끝내는 것. 회원 본인이 하는 "자진 탈퇴"와 관리자가 하는 "강제 탈퇴"가 있다 |
| 포인트 | 결제에 쓸 수 있는 회원별 적립금. 단위 P, 1P 단위 정수 |
| 포인트 잔액 | 회원이 지금 가진 포인트 |
| 포인트 내역 | 포인트가 바뀐 한 건의 기록. 적립·사용·복구·회수·지급·소멸 6종. "포인트 이력"과 같은 개념이며 "내역"으로 쓴다 |
| 적립 | 결제가 확정된 직후 결제 금액의 1%를 늘리는 것 |
| 사용 | 결제할 때 포인트로 금액 일부(또는 전부)를 내는 것 |
| 복구 | 환불할 때 그 결제에서 쓴 포인트를 돌려주는 것 |
| 회수 | 환불할 때 그 결제로 적립했던 포인트를 거두는 것 |
| 지급 | 관리자가 사유를 적어 회원의 포인트를 늘리는 것 |
| 소멸 | 회원이 탈퇴할 때(자진·강제 모두) 남은 잔액을 0으로 만드는 것. 시간이 지나 사라지는 것이 아니다 |
| 결제 금액 | 예약 총액에서 사용 포인트를 뺀, 회원이 실제로 낸 금액 |

## 불변식

### 1. 회원가입

- REQ-1. 회원가입으로 만들 수 있는 역할은 고객과 상점주뿐이다. 관리자는 회원가입으로 만들 수 없다.
- REQ-2. 가입할 때 이메일·비밀번호·역할·이름·전화번호 5가지를 모두 정해야 한다. 새로 가입하는 회원부터 적용한다. 이미 가입한 회원은 이름·전화번호가 비어 있어도 되지만 내 정보를 바꿀 때는 둘 다 채워야 한다. 관리자는 예외로 이름·전화번호가 없어도 된다(경계 절 B-5).
- REQ-3. 이메일은 앞뒤 공백을 빼고 소문자로 바꾼 뒤 판단한다. 바꾼 값은 1자 이상 255자 이하이고, 중간에 공백이 없으며, `@`가 정확히 1개이고, `@` 앞과 뒤가 모두 비어 있지 않으며, `@` 뒤에 `.`이 1개 이상 있다.
- REQ-4. 같은 이메일(REQ-3로 바꾼 값 기준)로는 회원이 둘 이상 있을 수 없다. 이미 쓰인 이메일(탈퇴한 회원의 이메일 포함)로는 가입할 수 없다.
- REQ-5. 비밀번호는 공백만으로 이루어질 수 없고, 8자 이상이며, UTF-8 기준 72바이트 이하이다. 문자 종류(숫자·특수문자 포함 등) 규칙은 없다. 가입·변경·재설정 모두 이 규칙을 따른다.
- REQ-6. 이름은 공백만으로 이루어질 수 없고 1자 이상 100자 이하이다. 상점주의 이름은 상호이며, 상점주는 이름 칸 하나에 상호를 적는다.
- REQ-7. 전화번호는 공백만으로 이루어질 수 없고 1자 이상 100자 이하이다. 형식 규칙(숫자·하이픈 등)은 없다.
- REQ-8. 상점주 가입 때 사업자번호는 받지 않는다.
- REQ-9. 새로 가입한 회원의 포인트 잔액은 0이다.
- REQ-10. 회원의 역할은 가입 후 바뀌지 않는다.
- REQ-11. 고객은 가입 즉시 모든 고객 행위를 할 수 있다(별도 승인이 없다). 상점주의 가입 직후 상태는 경계 절 B-1을 따른다.

### 2. 로그인·로그아웃

- REQ-12. 로그인은 이메일(REQ-3로 바꾼 값)과 비밀번호가 모두 맞을 때만 성공한다. 이메일이 없는 경우와 비밀번호가 틀린 경우는 같은 실패로 다루며, 어느 쪽이 틀렸는지 알려 주지 않는다.
- REQ-13. 같은 계정으로 로그인에 연속 5회 실패하면 그 계정은 마지막 실패부터 10분 동안 잠긴다. 잠긴 동안에는 비밀번호가 맞아도 로그인할 수 없다.
  - REQ-13-1. 잠긴 사실은 비밀번호가 맞을 때만 알려 준다. 비밀번호가 틀리면 보통의 실패와 같게 보인다(REQ-12).
  - REQ-13-2. 로그인에 성공하면 실패 횟수가 0이 된다. 비밀번호 재설정을 마치면 실패 횟수가 0이 되고 잠금도 풀린다.
  - REQ-13-3. 잠긴 동안의 시도는 실패 횟수에 넣지 않고 잠금 시간도 늘리지 않는다. 잠금이 끝나면 실패 횟수를 0부터 다시 센다. 가입되지 않은 이메일로는 잠금이 생기지 않는다.
- REQ-14. 인증 토큰에는 회원 ID, 역할, 토큰 식별자, 만료 시각이 담긴다.
- REQ-15. 인증 토큰은 발급 후 30분이 지나면 무효이다(운영 설정으로 바꿀 수 있으며 1분 이상). 유효 시간을 늘리거나 새 토큰으로 바꿔 주는 행위는 없어서, 만료되면 다시 로그인해야 한다.
- REQ-16. 한 회원이 동시에 여러 개의 유효한 인증 토큰을 가질 수 있다(동시 로그인 허용, 상한 없음).
- REQ-17. 로그아웃은 그 요청에 쓴 인증 토큰 하나만 무효로 만든다. 같은 회원의 다른 토큰은 계속 유효하다.
- REQ-18. 로그아웃한 인증 토큰은 원래 만료 시각 전이라도 다시 쓸 수 없다. 이미 로그아웃한 토큰으로는 로그아웃도 다시 할 수 없다.
- REQ-19. 인증 토큰의 주인인 회원이 없거나 탈퇴했으면 그 토큰은 무효이다.
- REQ-20. 폐기 토큰 기록에는 토큰 식별자(비어 있을 수 없음)와 원래 만료 시각이 반드시 있다. 원래 만료 시각이 지난 기록은 지워도 된다. 정리는 관리자가 요청할 때만 하고 자동으로 하지 않는다.

### 3. 내 정보

#### 3.1 조회와 변경
- REQ-21. 회원은 자기 정보만 볼 수 있다. 보이는 항목은 회원 ID, 이메일, 이름, 전화번호, 역할, 포인트 잔액, 가입 시각이다. 비밀번호는 본인에게도 보여 주지 않는다.
- REQ-22. 회원은 자기 이름·전화번호·비밀번호를 바꿀 수 있다. 이메일과 역할은 바꿀 수 없다.
- REQ-23. 바꾼 값도 가입 규칙(REQ-5·6·7)을 따른다. 이름과 전화번호는 필수이므로 빈 값으로 바꿀 수 없고, 이름·전화번호가 비어 있는 기존 회원은 정보를 바꿀 때 둘 다 채워야 한다.
- REQ-24. 비밀번호를 바꾸려면 현재 비밀번호를 맞혀야 한다. 바꾸면 그 변경에 쓴 인증 토큰만 유효하게 남고 그 회원의 나머지 토큰은 무효가 된다.

#### 3.2 비밀번호 재설정
- REQ-25. 비밀번호를 잊은 회원은 로그인하지 않고도 비밀번호를 재설정할 수 있다.
- REQ-26. 재설정은 ① 회원이 이메일로 재설정을 요청 ② 시스템이 일회용 재설정 코드를 만들어 회원 본인에게 전달 ③ 회원이 코드와 새 비밀번호를 제출, 순서로 진행한다. 회원 본인임은 "가입한 이메일로 받은 재설정 코드"로 확인한다.
- REQ-27. 재설정 요청의 결과는 그 이메일이 가입되어 있는지와 관계없이 같게 보인다(가입 여부를 알려 주지 않음). 가입되지 않은 이메일과 탈퇴한 회원에게는 코드를 만들지 않는다.
  - REQ-27-1. 요청에 걸리는 시간의 차이로도 가입 여부를 짐작하기 어렵게 한다.
- REQ-28. 재설정 코드는 한 번만 쓸 수 있고, 유효 시간이 지나면 무효이다. 새 코드를 발급하면 그 회원의 이전 코드는 무효가 된다. 유효 시간은 15분이다.
- REQ-28-1. 같은 회원이 직전 코드 발급 후 60초 안에 다시 요청하면 새 코드를 만들지 않고 이전 코드를 그대로 둔다. 요청 결과는 똑같이 보인다(REQ-27). 무차별 대입 완화(재요청으로 5회 제한을 반복 초기화하는 것 방지)가 목적이다.
- REQ-29. 틀린 코드를 5회 내면 그 코드는 무효가 되고 새로 요청해야 한다. 코드는 맞았으나 새 비밀번호가 REQ-5를 어겨 실패한 경우는 횟수에 넣지 않고 코드도 유효한 채 남는다.
- REQ-30. 새 비밀번호는 REQ-5를 따른다.
- REQ-31. 탈퇴한 회원은 재설정할 수 없다.
- REQ-32. 재설정이 끝나면 그 회원의 모든 인증 토큰이 무효가 된다.

#### 3.3 자진 탈퇴
- REQ-33. 회원은 스스로 탈퇴할 수 있다.
- REQ-34. 탈퇴하면 그 회원의 예약과 포인트는 모두 사라진다. 뜻은 다음과 같다. ① 결제 대기 예약은 취소하고 재고를 돌려놓는다 ② 결제를 마친 예약은 취소하고 결제 금액을 전액 환불한다(위약금 없음, 환불에 따른 포인트 복구·회수 포함). 단, 픽업 마감(`pickup_end`)이 지난 결제 완료 예약(미수령)은 취소·환불·재고 복구를 하지 않고 그대로 남긴다([입력] 사용자 결정 2026-11-10(미수령 A안, PR #57, design/reservations.md D-46)) ③ 이미 픽업했거나 취소된 예약 기록은 지우지 않고 남기되, 탈퇴 후에는 본인도 볼 수 없다 ④ ①~③을 마친 뒤 남은 포인트 잔액을 0으로 만들고 "소멸" 내역을 한 건 남긴다. 기존 포인트 내역은 지우지 않는다. 남은 잔액이 이미 0이면 소멸 내역을 남기지 않는다(변동량 0인 내역은 없음, REQ-53).
- REQ-34-1. 자진 탈퇴와 관리자 강제 탈퇴는 예약·포인트를 똑같이 처리한다(REQ-34).
- REQ-35. 탈퇴한 회원(자진·강제 모두)은 로그인할 수 없고(없는 계정과 같은 실패), 이미 받은 인증 토큰도 무효이며, 어떤 정보도 바꿀 수 없다. 같은 이메일로 다시 가입할 수 없다.
  - REQ-35-1. 탈퇴하면 그 회원의 재설정 코드는 지운다(자진·강제 모두).
- REQ-36. 자진 탈퇴하려면 현재 비밀번호를 다시 맞혀야 한다. 관리자는 자진 탈퇴할 수 없다. 상점주는 자기 상점에 다른 고객의 결제 완료 예약 중 픽업 마감 전인 것이 남아 있으면 탈퇴할 수 없다. 미수령 예약은 탈퇴를 막지 않는다(강제 탈퇴 규칙 admin.md D13과 같음, [입력] 사용자 결정 2026-11-10(미수령 A안, PR #57, design/reservations.md D-46)).

### 4. 포인트

#### 4.1 잔액
- REQ-37. 포인트 잔액은 0 이상 2,147,483,647 이하인 정수이며 어떤 경우에도 음수가 되지 않는다.
- REQ-38. 역할과 관계없이 모든 회원이 포인트를 쌓고 쓸 수 있다.
- REQ-39. 포인트에는 유효기간이 없고, 시간이 지나 사라지지 않는다. 잔액이 소멸하는 경우는 탈퇴(REQ-34)뿐이다.
- REQ-40. 포인트는 결제·환불 처리, 관리자 지급, 탈퇴 시 소멸로만 바뀐다. 회원이 직접 자기 포인트를 늘리거나 줄이는 행위는 없다.
- REQ-41. 잔액이 바뀔 때마다 같은 금액의 포인트 내역이 한 건 남고, 잔액 변경과 내역은 함께 일어나거나 함께 일어나지 않는다.

#### 4.2 사용 (결제할 때)
- REQ-42. 포인트는 100P 단위로만 쓸 수 있다. 따라서 한 번에 쓸 수 있는 최소량은 100P이다.
- REQ-43. 결제 1건에 쓰는 포인트는 잔액 이하이면서 그 예약 총액 이하이다.
- REQ-44. 예약 총액 전부를 포인트로 내는 것(결제 금액 0원)이 가능하다. 총액이 100원 단위가 아니면 끝자리는 포인트로 낼 수 없다.
- REQ-45. 결제가 실패하면 그 결제에 쓰려던 포인트는 쓰지 않은 것으로 되돌아간다.

#### 4.3 적립 (결제 확정 후)
- REQ-46. 결제가 확정되면 바로 결제 금액의 1%를 적립한다. 소수점 아래는 버린다.
- REQ-47. 적립 기준은 결제 금액(포인트로 낸 부분 제외)이다. 결제 금액이 99원 이하이거나 0원이면 적립이 없다.
- REQ-48. 적립된 포인트는 적립 즉시 다음 결제에 쓸 수 있다(별도 대기 기간이 없다).

#### 4.4 환불할 때 (복구·회수)
- REQ-49. 환불하면 그 결제에서 쓴 포인트(예약 총액 − 결제 금액)를 위약금 여부와 상관없이 전부 돌려준다.
- REQ-50. 환불하면 그 결제로 적립했던 포인트(결제 금액의 1%)를 거둔다. 잔액보다 많이 거두지 않으며, 모자란 만큼은 포기한다(빚이나 음수 잔액이 생기지 않음). 실제로 거둔 양이 0이면 내역을 남기지 않는다.
- REQ-51. 결제 1건은 한 번만 환불되므로 복구·회수도 결제당 한 번만 일어난다.

#### 4.5 지급
- REQ-52. 관리자만 회원에게 포인트를 지급할 수 있고, 지급할 때 사유를 반드시 적는다. 지급은 늘리기만 하며 관리자가 포인트를 차감하는 행위는 없다. 지급 대상·금액 한도는 admin 요구 조건에서 정한다(경계 절 B-6).

#### 4.6 포인트 내역
- REQ-53. 포인트 내역의 변동량은 0이 아니다. 적립·복구·지급은 양수, 사용·회수·소멸은 음수이다. 소멸 내역의 변동량은 소멸 직전 잔액의 음수이며 변경 후 잔액은 0이다.
- REQ-54. 포인트 내역은 한 번 남으면 바꾸거나 지울 수 없다.
- REQ-55. 새로 남는 모든 내역에는 변경 후 잔액(0 이상)이 함께 남는다. 지급 내역에는 사유와 지급한 관리자가 반드시 남고, 적립·사용·복구·회수·소멸 내역에는 사유·처리자가 없다(소멸은 탈퇴에 따른 처리라 탈퇴 기록이 근거가 된다). 이미 있는 내역의 변경 후 잔액은 비워 둔다.
- REQ-56. 회원은 자기 포인트 내역만 볼 수 있다. 잔액과 함께 최신순(같은 시각이면 나중에 남은 것 먼저)으로 보이며, 종류로 걸러 볼 수 있다.
- REQ-57. 내역은 한 번에 1건 이상 100건 이하로 나눠 보며, 정하지 않으면 20건씩 본다.

## 다른 모듈과의 경계

> 아래는 다른 모듈(주로 관리자 모듈 `docs/design/admin.md`, 팀원 담당)이 정하는 규칙 가운데 **auth가 지켜야 하는 것**만 적는다. 상세 규칙은 admin 요구 조건에서 결정한다.

- B-1. 상점주 계정: 역할 값은 `OWNER`이다. 상점주는 가입 직후 승인 대기 상태이며 관리자가 승인해야 상점을 열 수 있다. 승인 대기·거부 상점주도 로그인할 수 있고, 상점 개설·폐점만 할 수 없다.
- B-2. 정지된 회원: 정지 종료 시각이 지나면 자동으로 정지가 풀린 것으로 본다. 정지된 상점주는 로그인할 수 있고 자기 상점의 기존 예약 픽업 처리만 할 수 있다. 정지된 고객은 로그인할 수 없고(정지 사실은 비밀번호가 맞을 때만 알림), 정지 즉시 이미 받은 토큰으로도 모든 회원 행위를 할 수 없으나 로그아웃은 할 수 있다.
- B-3. 강제 탈퇴: 기록은 남는다(논리 삭제). 예약·포인트 처리, 로그인·토큰·이메일은 자진 탈퇴와 같다(REQ-34, REQ-34-1, REQ-35). 강제 탈퇴도 결제 대기 예약을 취소하고, 남은 포인트를 소멸 내역과 함께 0으로 만든다.
- B-4. 포인트 지급: auth는 내역 종류 "지급"을 갖고(REQ-53), 지급 내역에 사유·관리자를 남긴다(REQ-55). 관리자는 포인트를 지급만 할 수 있고 차감할 수 없다(REQ-52).
- B-5. 관리자 계정 생성(auth 소관, 확정): 운영자가 서버 시작 설정에 관리자 이메일·비밀번호를 둘 다 지정할 때만 만든다. 같은 이메일의 관리자가 있으면 아무것도 바꾸지 않고, 관리자가 아닌 회원이 있으면 관리자로 바꾸지 않고 실패한다. 비밀번호 규칙은 REQ-5와 같다. 새 관리자의 잔액은 0이다. 관리자는 이름·전화번호가 없어도 된다.
- B-6. admin 요구 조건에서 결정할 항목(auth 질문 아님, 메모): 정지 대상 조건·재정지·무기한 정지 해제 수단(admin.md D36, D10 후속), 정지·거부·탈퇴·지급 사유 길이(D27), 상점 연쇄 정지(D11), 거부 후 재심사(§3.1.2), 관리자 강제 탈퇴 불가·탈퇴 사유 보관(§3.1.3, D14), 상점주 강제 탈퇴 시 상점 폐점 처리(D13), 관리자 포인트 지급 대상·한도(D24), 다른 회원 포인트 내역 조회(EP 8), 관리자 계정 수 상한.

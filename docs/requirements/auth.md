## 1. 회원가입

- REQ-1. 회원가입으로 만들 수 있는 역할은 고객과 상점주뿐이다. 관리자는 회원가입으로 만들 수 없다. [입력] user.py:14-19, reference/auth.md:27
- REQ-2. 가입할 때 이메일·비밀번호·역할·이름·전화번호 5가지를 모두 정해야 한다. 새로 가입하는 회원부터 적용한다. 이미 가입한 회원은 이름·전화번호가 비어 있어도 되지만 내 정보를 바꿀 때는 둘 다 채워야 한다. 관리자는 예외로 이름·전화번호가 없어도 된다(경계 절 B-5). [입력] 사용자 답변 RQ-1
- REQ-3. 이메일은 앞뒤 공백을 빼고 소문자로 바꾼 뒤 판단한다. 바꾼 값은 1자 이상 255자 이하이고, 중간에 공백이 없으며, `@`가 정확히 1개이고, `@` 앞과 뒤가 모두 비어 있지 않으며, `@` 뒤에 `.`이 1개 이상 있다. [입력] user.py:64-76
- REQ-4. 같은 이메일(REQ-3로 바꾼 값 기준)로는 회원이 둘 이상 있을 수 없다. 이미 쓰인 이메일(탈퇴한 회원의 이메일 포함)로는 가입할 수 없다. [입력] service.py:73-74, schema.sql:10, 사용자 답변 RQ-16
- REQ-5. 비밀번호는 공백만으로 이루어질 수 없고, 8자 이상이며, UTF-8 기준 72바이트 이하이다. 문자 종류(숫자·특수문자 포함 등) 규칙은 없다. 가입·변경·재설정 모두 이 규칙을 따른다. [입력] user.py:79-85, 사용자 답변 RQ-2, RQ-3
- REQ-6. 이름은 공백만으로 이루어질 수 없고 1자 이상 100자 이하이다. 상점주의 이름은 상호이며, 상점주는 이름 칸 하나에 상호를 적는다. [입력] user.py:45-46, 사용자 답변 RQ-1, RQ-14
- REQ-7. 전화번호는 공백만으로 이루어질 수 없고 1자 이상 100자 이하이다. 형식 규칙(숫자·하이픈 등)은 없다. [입력] user.py:47-48, 사용자 답변 RQ-1
- REQ-8. 상점주 가입 때 사업자번호는 받지 않는다. [입력] 사용자 답변 RQ-14
- REQ-9. 새로 가입한 회원의 포인트 잔액은 0이다. [입력] user.py:103, reference/auth.md:15
- REQ-10. 회원의 역할은 가입 후 바뀌지 않는다. [입력] design/auth.md §3.5 "상태 값(Role)은 전이가 없다"
- REQ-11. 고객은 가입 즉시 모든 고객 행위를 할 수 있다(별도 승인이 없다). [입력] docs/design/admin.md D4(확정). 상점주의 가입 직후 상태는 경계 절 B-1

## 2. 로그인·로그아웃

- REQ-13. 로그인에 실패한 횟수와 관계없이 다시 시도할 수 있다(시도 제한 없음). [입력] service.py:111-117, 사용자 답변 RQ-5
- REQ-14. 인증 토큰에는 회원 ID, 역할, 토큰 식별자, 만료 시각이 담긴다. [입력] token_claims.py:9-13, README:74-79
- REQ-15. 인증 토큰은 발급 후 30분이 지나면 무효이다(운영 설정으로 바꿀 수 있으며 1분 이상). 유효 시간을 늘리거나 새 토큰으로 바꿔 주는 행위는 없어서, 만료되면 다시 로그인해야 한다. [입력] settings.py:17, 34-38, README:79, 사용자 답변 RQ-7
- REQ-16. 한 회원이 동시에 여러 개의 유효한 인증 토큰을 가질 수 있다(동시 로그인 허용, 상한 없음). [입력] service.py:118, 사용자 답변 RQ-6
- REQ-17. 로그아웃은 그 요청에 쓴 인증 토큰 하나만 무효로 만든다. 같은 회원의 다른 토큰은 계속 유효하다. [입력] service.py:130-132, 사용자 답변 RQ-6

- REQ-19. 인증 토큰의 주인인 회원이 없거나 탈퇴했으면 그 토큰은 무효이다. [입력] service.py:125-127, 사용자 답변 RQ-16
- REQ-20. 폐기 토큰 기록에는 토큰 식별자(비어 있을 수 없음)와 원래 만료 시각이 반드시 있다. 원래 만료 시각이 지난 기록은 지워도 된다. 정리는 관리자가 요청할 때만 하고 자동으로 하지 않는다. [입력] token_blacklist.py:5-15, reference/auth.md:264, design/auth.md D-블랙리스트정리(확정)

## 3. 내 정보

### 3.1 조회와 변경
- REQ-21. 회원은 자기 정보만 볼 수 있다. 보이는 항목은 회원 ID, 이메일, 이름, 전화번호, 역할, 포인트 잔액, 가입 시각이다. 비밀번호는 본인에게도 보여 주지 않는다. [입력] reference/auth.md §4, schemas.py:20-29
- REQ-22. 회원은 자기 이름·전화번호·비밀번호를 바꿀 수 있다. 이메일과 역할은 바꿀 수 없다. [입력] 사용자 답변 RQ-2
- REQ-23. 바꾼 값도 가입 규칙(REQ-5·6·7)을 따른다. 이름과 전화번호는 필수이므로 빈 값으로 바꿀 수 없고, 이름·전화번호가 비어 있는 기존 회원은 정보를 바꿀 때 둘 다 채워야 한다. [입력] 사용자 답변 RQ-1, RQ-2
- REQ-24. 비밀번호를 바꾸려면 현재 비밀번호를 맞혀야 한다. 바꾸면 그 변경에 쓴 인증 토큰만 유효하게 남고 그 회원의 나머지 토큰은 무효가 된다. [입력] 사용자 답변 RQ-2, RQ-21

### 3.2 비밀번호 재설정
- REQ-25. 비밀번호를 잊은 회원은 로그인하지 않고도 비밀번호를 재설정할 수 있다. [입력] 사용자 답변 RQ-3
- REQ-26. 재설정은 ① 회원이 이메일로 재설정을 요청 ② 시스템이 일회용 재설정 코드를 만들어 회원 본인에게 전달 ③ 회원이 코드와 새 비밀번호를 제출, 순서로 진행한다. 회원 본인임은 "가입한 이메일로 받은 재설정 코드"로 확인한다. 이메일 발송 기능이 생기기 전 시연에서는 코드를 운영 기록에서 확인하는 임시 방식을 쓴다. [입력] 사용자 답변 RQ-3, RQ-19
- REQ-27. 재설정 요청의 결과는 그 이메일이 가입되어 있는지와 관계없이 같게 보인다(가입 여부를 알려 주지 않음). 가입되지 않은 이메일과 탈퇴한 회원에게는 코드를 만들지 않는다. [입력] 사용자 답변 RQ-19
- REQ-28. 재설정 코드는 한 번만 쓸 수 있고, 유효 시간이 지나면 무효이다. 새 코드를 발급하면 그 회원의 이전 코드는 무효가 된다. 유효 시간은 15분이다. [입력] 사용자 답변 RQ-3, RQ-20

## 다른 모듈과의 경계

> 아래는 다른 모듈(주로 관리자 모듈 `docs/design/admin.md`, 팀원 담당)이 정하는 규칙 가운데 **auth가 지켜야 하는 것**만 적는다. 상세 규칙은 admin 요구 조건에서 결정한다. B-1~B-5는 모두 코드에 반영되어 있다(2026-11-06 대조). `docs/design/admin.md`의 D12·D24·D35·D43과 정지 회원 로그아웃 서술은 이 절과 달라 설계 문서 갱신이 필요하다(admin 담당).

- B-1. 상점주 계정: 역할 값은 `OWNER`이다([입력] 사용자 답변 RQ-13). 상점주는 가입 직후 승인 대기 상태이며 관리자가 승인해야 상점을 열 수 있다([입력] docs/design/admin.md D4 확정, reference/stores.md:59). 승인 대기·거부 상점주도 로그인할 수 있고, 상점 개설·폐점만 할 수 없다([입력] 사용자 답변 RQ-13).
- B-2. 정지된 회원: 정지 종료 시각이 지나면 자동으로 정지가 풀린 것으로 본다([입력] admin.md D10 확정). 정지된 상점주는 로그인할 수 있고 자기 상점의 기존 예약 픽업 처리만 할 수 있다([입력] admin.md D35·D39 확정). 정지된 고객은 로그인할 수 없고(정지 사실은 비밀번호가 맞을 때만 알림), 정지 즉시 이미 받은 토큰으로도 모든 회원 행위를 할 수 없으나 로그아웃은 할 수 있다([입력] 사용자 답변 RQ-15). 코드 반영됨(로그아웃은 정지 회원 허용). `docs/design/admin.md:392`의 "로그아웃은 403" 서술은 갱신 대상이다.
- B-3. 강제 탈퇴: 기록은 남는다(논리 삭제). 예약·포인트 처리, 로그인·토큰·이메일은 자진 탈퇴와 같다(REQ-34, REQ-34-1, REQ-35, [입력] 사용자 답변 RQ-16). 예약 취소·전액 환불은 admin.md D12(확정)와 같다. 코드 반영됨: 강제 탈퇴도 결제 대기 예약을 취소하고 남은 포인트를 소멸 내역과 함께 0으로 만든다. `docs/design/admin.md` D12(결제 대기 예약은 대상 아님)·D24 서술은 갱신 대상이다.
- B-4. 포인트 지급: auth는 내역 종류 "지급"을 갖고(REQ-53), 지급 내역에 사유·관리자를 남긴다(REQ-55). design/auth.md D-포인트비공개의 "관리자 수동 조정 없음"은 "관리자 지급만 허용, 차감 없음"으로 바뀌었다([입력] 사용자 답변 RQ-17). design/auth.md 갱신은 설계 담당 몫이다.
- B-5. 관리자 계정 생성(auth 소관, 확정): 운영자가 서버 시작 설정에 관리자 이메일·비밀번호를 둘 다 지정할 때만 만든다. 같은 이메일의 관리자가 있으면 아무것도 바꾸지 않고, 관리자가 아닌 회원이 있으면 관리자로 바꾸지 않고 실패한다. 비밀번호 규칙은 REQ-5와 같다. 새 관리자의 잔액은 0이다. [입력] settings.py:48-61, service.py:83-109, user.py:118, reference/auth.md:288-298, design/auth.md D-관리자생성. 관리자는 이름·전화번호가 없어도 된다([입력] 사용자 답변 RQ-1).
- B-6. admin 요구 조건에서 결정할 항목(auth 질문 아님, 메모): 정지 대상 조건·재정지·무기한 정지 해제 수단(admin.md D36, D10 후속), 정지·거부·탈퇴·지급 사유 길이(D27), 상점 연쇄 정지(D11), 거부 후 재심사(§3.1.2), 관리자 강제 탈퇴 불가·탈퇴 사유 보관(§3.1.3, D14), 상점주 강제 탈퇴 시 상점 폐점 처리(D13), 관리자 포인트 지급 대상·한도(D24), 다른 회원 포인트 내역 조회(EP 8), 관리자 계정 수 상한. [입력] docs/design/admin.md §3.1, §11

### RQ-4. 회원이 스스로 탈퇴할 수 있게 할까요?
대상: REQ-33~36, 회원 계정 전이, 소멸 절
배경: 지금은 회원 탈퇴가 관리자 처리(admin.md EP 4)로만 설계되어 있고 본인 탈퇴는 명세·코드에 없습니다.
제안: 이번 범위에서는 없음 — 근거: 명세에 기능이 없음. 넣는다면 관리자 탈퇴와 같은 처리(확정 예약 취소·환불, admin.md D12)를 제안

사용자: 제안대로
반영: REQ-34, REQ-35, REQ-36, 용어 "소멸", REQ-39·40·53·55, 주체와 정책 "자진 탈퇴"·"포인트 소멸", 회원 계정 전이, 소멸 절 (2회차)

### RQ-16. (경계) 탈퇴한 회원의 로그인·이메일·남은 포인트는 어떻게 다룰까요?

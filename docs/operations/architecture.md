# 아키텍처 원칙 (4계층 · DDD)

이 문서는 계층 책임과 도메인 설계 원칙을 정합니다. 코드 패턴의 정본은 `.claude/skills/layer-implementation/SKILL.md`, 자동 검사 규칙의 정본은 `.claude/skills/layer-check/SKILL.md`입니다. 이 문서와 `src/auth/**` 코드가 다르면 auth 코드를 따르고 이 문서를 고칩니다.

## 1. 계층 책임

| 계층 | 책임 | 위치 |
| --- | --- | --- |
| 표현 (Presentation) | 요청·응답 검증(Pydantic), 인증 의존성, 구현체 조립(주입) | `<모듈>/presentation/schemas.py`, `router.py` |
| 응용 서비스 (Application) | 유스케이스 흐름, 트랜잭션 경계, 다른 모듈 조합 | `<모듈>/application/service.py` |
| 도메인 (Domain) | 도메인 규칙·모델(엔티티, VO, 애그리거트), 도메인 예외, 추상 포트 | `<모듈>/domain/*.py` |
| 인프라 (Infrastructure) | DB 모델, 레포지토리 구현체, 외부 기능 구현 | `<모듈>/infrastructure/models.py`, `repositories.py` |

## 2. 의존 방향

- presentation → application → domain
- application → infrastructure → domain
- presentation은 infrastructure를 직접 참조하지 않는다.
- domain은 순수 파이썬이다. fastapi, sqlalchemy, pydantic, `database`, 다른 계층을 import하지 않는다.
- 모듈 사이 협력은 상대 모듈의 application 서비스로만 한다. 상대 모듈의 레포지토리·모델을 직접 쓰지 않는다.
- 같은 트랜잭션으로 묶이면 상대 서비스를 `commit=False`로 부르고, 호출한 서비스가 마지막에 한 번 `commit()`한다.

## 3. 도메인 설계

### 3.1 도메인 지식과 유비쿼터스 언어
- 도메인 계층은 비즈니스가 해결할 문제에 대한 지식을 코드로 표현한다.
- 코드·문서·대화에서 같은 용어를 쓴다. 용어의 정본은 `docs/reference/<모듈>.md`(API 명세)와 `db-schema` 스킬의 테이블·컬럼명이다.
- 새 용어가 필요하면 설계안에 정의하고 명세와 맞춘다.

### 3.2 도메인 모델
- 비즈니스 요구사항(도메인 규칙)은 도메인 메서드로 구체화한다.
- 서비스에 비즈니스 if-else를 두지 않는다. 서비스는 `조회 → 도메인 메서드 → save() → commit()`만 조율한다.
- 규칙 위반은 모듈 전용 도메인 예외(`<모듈>/domain/exceptions.py`)로 낸다. HTTP 응답 변환은 `src/error_handlers.py`의 전역 핸들러가 한다.

### 3.3 애그리거트 (Aggregate)
- 같은 책임과 일관성을 보장하는 객체의 묶음이다. 루트 엔티티와 값 객체(VO)로 구성된다.
- 내부 VO는 루트 엔티티를 통해서만 읽고 바꾼다.
- 하나의 트랜잭션은 원칙적으로 하나의 애그리거트만 변경한다. 여러 애그리거트를 바꿔야 하면 설계안에 트랜잭션 경계와 잠금 순서를 적는다.

### 3.4 바운디드 컨텍스트 (Bounded Context)
- 같은 실체도 책임마다 요구하는 속성이 다르다(회원·작성자·주문자).
- 모듈은 자기 책임에 필요한 속성만 가진 표현을 쓴다. 다른 모듈의 엔티티를 그대로 끌어다 쓰지 않는다.

### 3.5 도메인 이벤트와 모듈 간 요청
- 자기 책임 밖의 일은 해당 모듈에 요청한다.
- 현재 요청 수단은 상대 모듈 application 서비스 호출이다. 비동기 이벤트 버스를 도입하려면 설계안에서 먼저 결정한다.

## 4. 추상화와 주입

### 4.1 원칙
- 레포지토리와 외부 기능(도메인 서비스가 접근하는 외부 기능 포함)은 추상(포트)으로 정의하고, 인프라 계층에서 구현하며, 조립 지점(Container)에서 응용 서비스에 구현체를 주입한다.

### 4.2 이 프로젝트의 적용
- 조립 지점(Container)은 presentation의 FastAPI `Depends` 의존성 함수다.
- 응용 서비스는 생성자 키워드 인자로 레포지토리·포트를 받는다. 테스트는 fake를 주입해 DB 없이 검증한다(`src/auth/application/service.py` 참고).
- 모듈 사이 의존은 반드시 포트로 끊는다. 포트는 **쓰는 쪽** 모듈이 정의한다(`typing.Protocol` 또는 ABC).
- 레포지토리 추상화 방식은 auth 코드를 따른다. 방식을 바꾸려면 전 모듈에 함께 적용하는 결정을 먼저 하고, 한 모듈만 다르게 만들지 않는다.

### 4.3 순환 의존 금지
- 두 모듈이 서로를 필요로 하면 양쪽 모두 포트를 정의하고, 구현체 연결은 presentation에서만 한다.
- 서비스끼리 서로를 생성자 안에서 만들지 않는다(무한 재귀). 조립 순서는 의존성 함수에서 한 방향으로 정한다.

## 5. 데이터 무결성
- 스키마의 정본은 `.claude/skills/db-schema/`의 `SKILL.md`와 `schema.sql`이다. 바꿀 때는 두 파일을 함께 고친다.
- 마이그레이션 도구가 없으면 스키마 변경 후 개발 DB를 다시 만든다.
- DB 제약으로 막을 수 없는 규칙(시간 조건이 붙은 유일성, 테이블을 넘나드는 검사)은 행 잠금(`with_for_update`)과 도메인 검증으로 막고, 설계안에 근거를 적는다.
